# 2 · Class rank on the Rankings Overview (`48b68db`)

`Cls Rk` sits directly after `Rank` in **Core** and **Composites** (and so in
**All**, and in the CSV). The rows already carried `ClassRank` / `ClassOf`, so
this was columns, not engine work.

Rendered **`#3 of 74`**, not `#3`. A rank that does not name its pool is the
house's oldest rule (`cards.pctile_bar`), and §5 below is what breaking it
looks like in public.

### The build turned up a real defect, bigger than the brief warned

The brief said an out-of-state team "may have none". The truth is worse: the
class column holds the **literal string `'N/A'`** far more often than `NULL`,
and `class_label` resolves both to the same display label. So the obvious
blank-only guard passes `'N/A'` straight through — and `_assign_ranks` buckets
on `(state, class)`, which means **21 separate `(state, 'N/A')` ladders all
render under the one label `'N/A'`**. Measured: **230 classless girls teams**.

The new column prints an em dash for them. The test caught it by asserting
class rank rises with overall rank inside every class — 3 inversions before the
guard, 0 after.

**And the same defect was already on screen.** `ui.rank_chip` takes
`class_lbl` + `ClassRank` at all three of its call sites — Rankings' recent
results, Schedule's game-of-the-day hero, and Schedule's result cards — and was
rendering `N/A #63` and `N/A #24` **side by side on one score card, from
different ladders, neither of them a class rank**. It now returns `""` for a
classless team, which is the one definition all three inherit.

### The "as of" board — checked, and deliberately left alone

`rating_snapshots` is `(day, gender, system, team_id, season, rating, rank)`.
**No class, no class rank.** That branch cannot carry one without re-deriving it
over a field already truncated to `MIN_SNAPSHOT_GP`, which would state a pool
that is not the class's real size. Left as it is.

# 3 · The live app (`01ecb3a`)

## The public rank — your ruling, built

Option 3. The league-wide ordinal is **gone from every public payload**:
`rank`, `of`, `rank_of`, `opp_rank`. Verified on production after deploy — the
`/api/public/teams` keys are now `class_lbl, class_of, class_rank, gender, gp,
id, losses, name, short, state, wins`.

The Teams list is ordered by the **class ladder**, so the first screen is the
eight class leaders and picking one chip gives that class top to bottom. Every
rank states its pool: badge carries the number, the line beside it carries
`OK 3A · Boys · of 64 in class`. **Gaps are now structurally impossible** — the
number and the list come from the same pool.

Booker T Washington reads **OK 5A #1** instead of sitting below two 1-0
out-of-state teams.

Same `'N/A'` defect closed here too: a class rank is published only for a team
that *has* a class. The record still is — the record is a fact, the rank was
not.

## Short names

Written **once**, in `public_feed.short_name`, and carried in all four payloads,
because the live pages are plain JS and cannot import the Python helper. Two
rules would drift, and the two that drifted would be the game hero and the
linescore — side by side on one screen.

```
Claremore (Sequoyah) Girls           -> Claremore
North Little Rock (Little Rock, Ark) -> North Little Rock
PARIS NORTH LAMAR HIGH SCHOOL        -> PARIS NORTH LAMAR
McDonald County, MO 5a school        -> McDonald County
Central (Sallisaw) Girls             -> Central (Sallisaw)    <- fits: kept
BOOKER T WASHINGTON Boys             -> BOOKER T WASHINGTON   <- no noise to cut
```

Two rules in there worth knowing:

* **The parenthetical is dropped only when the name does not already fit.**
  `Central (Sallisaw)` and `Central (Tulsa)` are two different schools and an
  unconditional strip prints them as the same team on the same scoreboard.
* **It never writes an ellipsis.** What it cannot shorten it returns whole for
  CSS to cut at the real edge of the box — a truncation this function writes
  (`Booker T…`) is worse than the browser's.

Full names stay in the `<title>`, the team-page header and the search index.

Measured at 375 px: **the officiating table now fits without horizontal
scroll**, because its header is two short names. That is the assigner tool, and
it got better rather than trimmed.

# 5 · The 23 `season='Current'` games — the premise was wrong (`8d60884`)

FREEZE_PUNCHLIST §6 asked whether `auto_season_rollover.py` relabels them "or
November opens on an empty schedule". Measured against a snapshot pulled from
production today: **there was never anything to relabel, and November is fine.**

`SEAS.ACTIVE` — the literal string `'Current'` — **is the stamp an
active-season row carries.** `execute_rollover` replaces it with a real label on
the way *out* of a season, which is why every row currently in the active season
has it. Production's `active_season` is already **2026-2027**, and those 23
games are dated 2026-12-08 → 2027-02-16, inside 2026-2027. They are stamped
correctly.

Driven through the real decision function against the production snapshot:

```
2026-09-12: rolled=False  up-to-date   active=2026-2027 | Current=23
2026-10-01: rolled=False  up-to-date   active=2026-2027 | Current=23
2026-11-15: rolled=False  up-to-date   active=2026-2027 | Current=23
2027-02-16: rolled=False  up-to-date   active=2026-2027 | Current=23
2027-10-01: rolled=True                active=2027-2028 | Current=0, 2026-2027=23
```

The timer is **right** to do nothing this October: the season already rolled.

**So the risk here is the fix, not the defect.** Hand-stamping those rows
`'2026-2027'` — the obvious reading of the punch-list item — is the change that
would actually empty the schedule, because an active-season read looks for the
sentinel and a hand-stamped fixture answers to no active-season read for the
whole year it is live in. `tracker/test_season_sentinel_fixtures.py` pins that,
counterfactual included.

**Punch-list §6 can be struck.**

# 8 · The one design call left — the Event Editor's last mile

The scrub's deeper point survives: it is still five tools, and it thought two of
them wanted rethinking. It never said which two. My read, for you to accept or
reject:

* **"Add an event" and "Lineups" are the odd pair.** Every other tool starts
  from *find the row that is wrong*; these two start from *a thing that is not
  in the log at all* — a play nobody recorded, and a substitution nobody
  recorded. They are the same job (recover something missing) wearing two
  different shapes, and they are the two the filters never governed, which is
  why last night's restructure had to special-case them.
* The cheap version is to put them behind one **"Add what's missing"** tool with
  a two-way choice inside.
* The honest alternative is that they are both rare enough on a laptop that
  they belong on the phone, next to "Edit log", and the page keeps the three
  tools that genuinely need a big screen.

I have not built either. Say which and it is a short job.
